Memory & Swap — Deep Dive Reference

Diagnose RAM exhaustion, Linux Page Cache vs Available Memory, Swap paging activity, and OOM-Killer crash prevention.

🧠 The Linux Memory Myth: Free vs Available
In Linux, low free RAM is normal! The Linux kernel uses unused RAM as buff/cache for fast disk I/O. Always look at the available column — this is the true memory available before OOM thrashing occurs!
🧠 Concept 1: Free vs Available Memory & Page Cache
In Linux, low free memory is normal! Unused RAM is automatically allocated to buff/cache (file system page cache) to accelerate file read operations.
• Rule: Always check the available column in free -h. This reflects the true remaining memory that kernel can immediately assign to new processes without swapping.
🔄 Concept 2: Memory Paging, Swap Thrashing & Swappiness (0-100)
When physical RAM is depleted, kernel writes inactive pages to swap storage.
• Swap Thrashing: Continuous swap-in (si) and swap-out (so) operations severely degrade application performance.
• vm.swappiness=10: Reduces kernel tendency to swap physical pages, preserving RAM for databases (PostgreSQL, Redis) and Spark/JVM runtimes.
💥 Concept 3: OOM-Killer Architecture & badness Score
When physical RAM and swap are completely exhausted, kernel triggers Out-Of-Memory (OOM) Killer.
• Kernel computes an oom_score for every active process based on memory usage percentage and oom_score_adj tuning.
• Process with highest badness score is sent SIGKILL (137).

🧠 Application OOM Killed / Crash (Exit Code 137)

Memory & Swap
🎯 Triage Strategy & Intention Logic:
• RAM Headroom: Inspect available memory headroom (ignore free, focus strictly on available). • Kernel OOM Trace: Verify Linux Kernel OOM killer terminations in dmesg (Exit Code 137 / SIGKILL).
Step 1: Memory Scan
free -h
Check available RAM headroom and swap usage (ignore free, look at available)
Step 2: Confirm OOM
dmesg -T | grep -i oom
Trace kernel ring buffer logs for OOM killer executions (Exit Code 137)
Step 3: Top RSS Consumer
ps -eo pid,%mem,rss,cmd --sort=-rss
Identify the process consuming the highest resident physical memory (RSS)
Step 4: Remediation
sysctl vm.swappiness=10
Tune swappiness, tune application heap limits, or adjust container cgroup caps

💥 OOM-Killer Terminated Process

When available RAM reaches 0, kernel OOM-Killer kills the highest memory consumer. Check dmesg -T | grep -i oom to find the killed process.

🐌 High Swap Thrashing Latency

If vmstat 1 shows high si/so values, server is thrashing swap on disk. Set sysctl vm.swappiness=10 or add physical RAM.
